# Production Deployment

## Install fracture-ctl

Download the latest binary from [GitHub Releases](https://github.com/Sp0Q1/fracture-cms/releases):

```bash
curl -sL https://github.com/Sp0Q1/fracture-cms/releases/latest/download/fracture-ctl-linux-amd64.tar.gz \
  | tar xz -C ~/.local/bin/
```

Other platforms: `fracture-ctl-linux-arm64`, `fracture-ctl-macos-amd64`, `fracture-ctl-macos-arm64`.

## fracture-ctl Command Reference

| Command | Description |
|---------|-------------|
| `fracture-ctl init --image <img>` | Generate `.env` and `compose.prod.yaml` for production |
| `fracture-ctl init --image <img> --repo <url>` | Same, plus clone `assets/` and `config/` from the repo |
| `fracture-ctl init --dev` | Generate development `.env` (OIDC values filled by `setup.sh`) |
| `fracture-ctl up` | Pull latest image, auto-backup, start production services |
| `fracture-ctl down` | Stop all compose services |
| `fracture-ctl backup [-o file]` | Back up the database (SQLite or PostgreSQL) |
| `fracture-ctl restore <file> [--yes]` | Restore the database from a backup file |
| `fracture-ctl admin set <email>` | Promote a user to platform admin |
| `fracture-ctl admin list` | List all platform admins |
| `fracture-ctl ci` | Run all CI checks (fmt, clippy, semgrep, tests) via `dev/ci.sh` |
| `fracture-ctl dev [--setup]` | Start the dev stack; `--setup` runs `dev/setup.sh` first |
| `fracture-ctl update` | Self-update to the latest `ctl-v*` release |

## First-Time Deployment Walkthrough

No git clone needed. Just `fracture-ctl` and `podman`:

```bash
# 1. Create a project directory
mkdir my-app && cd my-app

# 2. Generate production config and clone assets
fracture-ctl init --image ghcr.io/your-org/your-app:latest \
                  --repo https://github.com/your-org/your-app.git

# 3. Configure OIDC, SMTP, database (all optional at first)
vim .env

# 4. Start the app
fracture-ctl up

# 5. (Optional) Promote yourself to platform admin after first login
fracture-ctl admin set you@example.com
```

`fracture-ctl init` generates `.env` (chmod 600) and `compose.prod.yaml`. If `--repo` is provided, it shallow-clones the repository (into `repo/`) so the app can mount its `assets/` and `config/`. The app boots immediately. OIDC and SMTP are optional -- edit `.env` and run `fracture-ctl up` again when ready.

## Configuration

### Environment Variables

Generate `.env` with `fracture-ctl init --image <image>`, then edit as needed:

| Variable | Required | Description |
|----------|----------|-------------|
| `APP_IMAGE` | Yes | Container image to deploy. Set by `init --image`. |
| `JWT_SECRET` | Yes | Session signing key. Auto-generated by `fracture-ctl init`. |
| `DATABASE_URL` | No | Default: SQLite. Set to `postgres://...` for PostgreSQL. |
| `OIDC_ISSUER_URL` | No | Identity provider URL. App works without it (login returns 503). |
| `OIDC_CLIENT_ID` | No | From your OIDC provider. |
| `OIDC_CLIENT_SECRET` | No | From your OIDC provider. |
| `OIDC_REDIRECT_URI` | No | `https://your-domain.com/api/auth/oidc/callback` |
| `OIDC_POST_LOGOUT_REDIRECT_URI` | No | `https://your-domain.com` |
| `MAILER_HOST` | No | SMTP host. Invite emails fail silently if not set. |
| `MAILER_PORT` | No | Default: 587 |
| `MAILER_USER` | No | SMTP username. |
| `MAILER_PASSWORD` | No | SMTP password. |

### Multi-tenant fleets

Running one deployment per tenant against a shared IdP? Read
[FEDERATION.md](FEDERATION.md) for the topology, the per-tenant trust
boundaries, and the `AUTH_ALLOWED_EMAIL_DOMAINS` admission control.

### OIDC Provider Setup

Register your app as an OIDC client in any provider (Keycloak, Auth0, Zitadel, etc.):

| Setting | Value |
|---------|-------|
| Application type | Web |
| Auth method | Client secret (Basic) |
| Grant type | Authorization code |
| Redirect URI | `https://your-domain.com/api/auth/oidc/callback` |
| Post-logout redirect URI | `https://your-domain.com` |
| Scopes | `openid`, `email`, `profile` |

Add the client ID, secret, and issuer URL to `.env`, then restart:

```bash
fracture-ctl up
```

### Using PostgreSQL

By default, the app uses SQLite (zero config). The generated `compose.prod.yaml`
contains only the `app` service; to switch to PostgreSQL you provide the
database yourself:

1. Uncomment the database lines in `.env` and comment out the SQLite
   `DATABASE_URL` (the app reads `DATABASE_URL` from `.env`):
   ```
   APP_DB_USER=fracture
   APP_DB_PASSWORD=<generated-password>
   DATABASE_URL=postgres://fracture:${APP_DB_PASSWORD}@db:5432/fracture
   ```
2. Add a `db` service to `compose.prod.yaml` (e.g. a `postgres:16-alpine`
   container with a volume and health check) and a `depends_on` from `app`, then:
   ```bash
   fracture-ctl up
   ```

A future `fracture-ctl init --database postgres` may generate the `db` service
for you; today it must be added manually.

## Migrations

The app uses `auto_migrate: true` in its Loco config. All pending migrations run automatically on startup -- no manual migration commands needed.

`fracture-ctl up` takes a pre-deploy backup before pulling the new image and restarting, so any migration that goes wrong can be rolled back:

```bash
fracture-ctl down
fracture-ctl restore .backup-pre-deploy-<timestamp>.sqlite --yes
fracture-ctl up   # redeploy the previous image tag
```

Pre-deploy backups are stored as `.backup-pre-deploy-<timestamp>.sqlite` in the project directory. The 3 most recent are kept; older ones are cleaned up automatically.

## Backups

### Manual Backup

```bash
fracture-ctl backup                     # backup-<timestamp>.sqlite or .sql
fracture-ctl backup -o my-backup.sqlite # custom filename
```

`fracture-ctl backup` auto-detects the database type from `.env`. For SQLite, it checkpoints the WAL and copies the file from the container. For PostgreSQL, it runs `pg_dump` inside the `db` container.

### Restore

```bash
fracture-ctl down                       # stop the app first
fracture-ctl restore backup-file --yes  # --yes skips confirmation prompt
fracture-ctl up                         # restart
```

For SQLite, the backup file is copied into the container and WAL/SHM files are cleaned up. For PostgreSQL, the SQL dump is piped into `psql`.

### Pre-Deploy Auto-Backup

Every `fracture-ctl up` automatically backs up the database before pulling and restarting, provided the app container is currently running. On a fresh start (no running container), the backup step is skipped.

## Platform Admin Management

Platform admins have access to admin-only features (blog management, cross-org job views, etc.). The user must have logged in at least once before they can be promoted.

```bash
fracture-ctl admin set admin@example.com   # promote to platform admin
fracture-ctl admin list                     # show all platform admins
```

`admin set` finds the user by email, locates the platform admin organization (creating it if it does not exist yet), and adds the user as an owner of that org. The user must have logged in at least once so that their account exists.

## Updating

### Update the app

```bash
fracture-ctl up
```

This pulls the latest image (as specified in `APP_IMAGE`), takes a pre-deploy backup, and restarts with `--force-recreate`. Migrations run automatically on boot.

### Update fracture-ctl itself

```bash
fracture-ctl update
```

Downloads the latest `ctl-v*` release from GitHub and replaces the current binary in place. fracture-ctl also checks for updates on every run and prints a notice if a newer version is available.

## Reverse Proxy

The app binds to `127.0.0.1:5150`. Put a reverse proxy in front for TLS.

A template nginx config is provided at `deploy/nginx.conf.template`:

```bash
sed 's/APP_DOMAIN/your-domain.com/g' deploy/nginx.conf.template \
  | sudo tee /etc/nginx/sites-available/your-app
sudo ln -sf /etc/nginx/sites-available/your-app /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d your-domain.com
```

## Troubleshooting

### OIDC discovery failed

The app logs `OIDC discovery failed` on startup when `OIDC_ISSUER_URL` is unreachable or not set. This is non-fatal -- the app boots and serves pages, but login returns 503. Fix:

- Verify `OIDC_ISSUER_URL` is correct and reachable from inside the container.
- Check DNS: the container needs `aardvark-dns` to resolve external hostnames. Install it: `sudo apt install aardvark-dns`.
- If using a self-hosted IdP on the same host, ensure the container can reach it (use the host IP, not `localhost`).

### No tables / database not initialized

If the app logs "no such table" errors:

- Verify `auto_migrate: true` is set in `config/production.yaml` under `database`.
- Check that the database file or PostgreSQL service is accessible.
- For SQLite, the data volume must be writable: `podman volume inspect` the `app_data` volume.
- For PostgreSQL, ensure the `db` service is healthy: `podman compose -f compose.prod.yaml ps`.

### Permission errors

- `.env` must be readable by the user running `podman compose` (chmod 600, owned by you).
- The `app_data` volume is managed by podman -- do not manually chmod files inside it.
- If `fracture-ctl backup` fails with "could not access SQLite database", install `sqlite3` on the host: `sudo apt install sqlite3`.

## Security Checklist

- [ ] `JWT_SECRET` is randomly generated (never reuse dev values)
- [ ] `.env` is `chmod 600` and not in version control
- [ ] TLS via reverse proxy (HTTPS only)
- [ ] Container binds to `127.0.0.1` (not `0.0.0.0`)
- [ ] Firewall allows only 80, 443, SSH
- [ ] OIDC redirect URIs match your production domain exactly
- [ ] Regular database backups scheduled
- [ ] Platform admin promoted via `fracture-ctl admin set`
